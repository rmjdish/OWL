Alongside the data dictionary, questionnaires, and topic pages, NSHD holds a large amount of documentation about how specific variables and datasets were built — data notes explaining a derivation, "topsheets" recording what a piece of cleaning work produced, corrections to a variable that turned out to be wrong, notes describing an entire derived dataset. Historically these have existed as standalone Word and PDF files, unconnected to OWL and to each other. If you didn't already know a document existed, you had no way to find it from a variable you were looking at, and no way to find the variables from the document.

This section closes that gap. Every document is turned into a page, cross-checked against the data dictionary to work out which variables it actually covers, and linked in both directions — from the document to its variables, and from each variable's own metadata page back to any document that mentions it. Where a document names variables clearly, you can add them straight to your basket without leaving the page.

The rest of this page explains how that works and why it's built the way it is — the two-way split between variable and dataset documentation, how automatic linking works and where it can't be trusted, and how variables get added to your basket from here.

Variable vs dataset documentation

Documentation is split into two kinds, and which one a document belongs to is decided by a person when it's added, not guessed automatically — more on why in the next section. The split matters because it's how you'd actually go looking for something: landing on a variable page wanting to know "was this ever corrected", versus scoping out a whole research topic and wanting to know what's been derived across the cohort.

Variable documentation

Documents about one specific variable, or a small tightly-related group. Typically short.

  • Topsheets — a structured record of a cleaning or derivation task, with an explicit field listing the output variable names
  • Variable notes — free-text notes about a specific variable, often documenting a bug, a fix, or a change in how it was constructed

Dataset documentation

Documents covering a whole derived dataset or an entire topic across many sweeps. Typically long, narrative, academic in style.

  • Data notes — a detailed write-up of how a dataset was constructed, often spanning many pages and referencing dozens of variables
  • Repeated-measures documentation — a single write-up covering a measure repeated at every sweep (height, weight, BMI), describing the whole family of variables at once
This split is set once, by whoever adds the document — it isn't inferred from the text. A repeated-measures document about anthropometry and a one-off note about a single variable can both be short, both have variable names in bold, and both be built the same way internally, so there's no reliable text pattern that tells "variable-level" and "dataset-level" apart. A person already knows which one it is; asking the software to guess would just introduce a chance of getting it wrong.

How documents get linked to variables

Every document is scanned for variable names using several methods, tried in order from most to least reliable. A document only needs to match one method to be linked — most match more than one.

Topsheet field — topsheets have an explicit "Output variables" field where the author lists exactly which variables the work produced. This is the most reliable source there is: someone deliberately typed these names to mean exactly this.
Bold heading — many notes use a variable name as a bolded heading or caption directly above a table or a definition. If that bolded text exactly matches a real variable name, it's treated as a confident match.
Sweep-pattern — some documents write a variable as a template, like HTyyU, alongside a list of the sweep years yy stands for. Recognising this pattern and substituting each year in turn is how a single mention like this can correctly resolve to eleven or more real variables, instead of only the one example the author happened to spell out in full.
Plain-text scan — the fallback for long narrative documents with no structured field, no bold headings, and no repeated pattern: any word in the body text that happens to exactly match a real variable name. This is the only method used on most dataset-level data notes, since they're written as continuous prose.

Confidence levels, and why nothing is automatic

The four methods above don't carry equal trust, and the difference matters more than it might sound. The dictionary holds over 28,000 variable names — with that many, a good number of them are short, ordinary-looking words. sex, own, hand, and inch are all genuine variable names. A plain-text scan of any document, on any topic, will turn some of these up purely by coincidence, with nothing to do with what the document is actually about.

So every match carries a confidence level based on which method found it, and the two ends of that scale are treated very differently on a document page:

  • High confidence — topsheet field, bold heading, or sweep-pattern matches. Shown up front, with a checkbox on every row — ticked if it's already in your basket — plus an Add all to basket button that ticks and adds every one in a single click.
  • Low confidence — plain-text scan matches. Shown collapsed, separately, with a short explanation of why they need a second look. There's no bulk action here — only the per-row checkbox, so nothing is added without someone specifically ticking that one variable.
Low-confidence matches are never added to a basket automatically, and never appear in an "Add all" action, however tempting it might be to widen that button to save clicks. A plain-text match being wrong isn't rare enough to risk — it's the expected outcome on any sufficiently long document.

When a variable has been renamed

Some documents describe a variable that no longer exists under the name written in the document. A note investigating a bug in a variable called SC53 might conclude with a fix that gets published under a different name entirely — sc53u, say — once the correction goes live. The note is still the correct, useful explanation of how sc53u came to be, but no amount of scanning its text against today's dictionary will ever find that connection, because SC53 simply isn't in the dictionary anymore.

Two things happen for a case like this:

  • A suggestion, automatically. Any bold text shaped like a variable name but missing from the dictionary is compared against every real variable name for a close spelling match. For SC53, this correctly proposes sc53u as the closest match, together with its label, so a reviewer can confirm it at a glance rather than searching by hand.
  • A confirmation, by a person. Once someone's checked a suggestion and agrees it's right, that gets recorded explicitly against the document — not inferred again every time the page rebuilds. From then on, the link between the old name in the note and the real current variable is as solid as any other match on the page.

The suggestion step exists to make the confirmation step fast, not to replace it. A spelling-similarity match is still a guess, and guesses about which variable a historical bug-fix note refers to are exactly the kind of thing that should have a person's name behind them before it's presented as fact.

Adding variables from a document

Every document page has a variables panel reflecting everything described above. High-confidence variables are listed with their labels in a green box, each with a checkbox that's already ticked if the variable is in your basket, plus a single Add all to basket button for taking the whole set in one click — this writes straight to your basket the same way every other "Add to basket" checkbox on OWL does, so it shows up immediately wherever else you're working. Low-confidence matches sit in a collapsed amber box beneath it, each with its own checkbox but no bulk option, so picking up a genuinely relevant plain-text match is still one click away — it's only the all-at-once action that's withheld there.

Where a document has a confirmed relationship to a variable under a different name — the renamed-variable case above — that variable is shown alongside the document's other high-confidence matches once confirmed, with a note explaining that it's linked via a historical name rather than a direct mention in the text.
