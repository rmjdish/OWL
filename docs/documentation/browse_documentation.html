Alongside the data dictionary, questionnaires, and topic pages, NSHD holds a large amount of documentation about how specific variables and datasets were built — data notes explaining a derivation, "topsheets" recording what a piece of cleaning work produced, corrections to a variable that turned out to be wrong, notes describing an entire derived dataset. Historically these have existed as standalone Word and PDF files, unconnected to OWL and to each other. If you didn't already know a document existed, you had no way to find it from a variable you were looking at, and no way to find the variables from the document.

This section closes that gap. Every document is turned into a page, cross-checked against the data dictionary to work out which variables it actually covers, and linked in both directions — from the document to its variables, and from each variable's own metadata page back to any document that mentions it. Where a document names variables clearly, you can add them straight to your basket without leaving the page.

The rest of this page explains how that works and why it's built the way it is — the different kinds of documentation you'll come across, how automatic linking works and where it can't be trusted, and how variables get added to your basket from here.

Kinds of documentation

Every document gets sorted into one of four kinds automatically, based on which of the structural patterns below it actually matches — the same detection used to find variable names in the first place (see the next section). Nothing here is tagged by hand: a document is a topsheet because it has a topsheet's structured "Output variables" field, not because someone filed it as one.

Topsheet — has the structured metadata table used to record a cleaning or derivation task, with an explicit "Output variables" field. This is the most common and most reliable kind, since the variable names it links to were deliberately typed by the person who did the work.
Variable note — no topsheet table, but uses a variable name as a bolded heading or caption somewhere in the text, whether or not that exact name still exists in today's dictionary (see "When a variable has been renamed" below). Typically a short note about one specific variable — a bug, a fix, a clarification.
Templated variable note — documents a variable written as a sweep template, like HTyyU, alongside a list of the years yy stands for. Common for a measure repeated at every sweep (height, weight, BMI), where one note describes the whole family of variables at once instead of eleven or more separate ones.
Narrative — none of the above: no topsheet table, no bold variable-shaped heading, no sweep template. The fallback for long-form, continuous-prose documents — typically a detailed data note covering a whole dataset or topic, referencing many variables in running text rather than a structured field.
Because this is structural, not topical, two documents that are both "about a whole dataset" in spirit can still land in different kinds if one happens to use a bolded variable-name caption and the other doesn't. The kind badge on each result in Browse the documentation tells you which pattern it matched — it's a hint about a document's shape, not a judgement of how important or how broad its subject is.

How documents get linked to variables

Every document is scanned for variable names using several methods, tried in order from most to least reliable. A document only needs to match one method to be linked — most match more than one.

Topsheet field — topsheets have an explicit "Output variables" field where the author lists exactly which variables the work produced. This is the most reliable source there is: someone deliberately typed these names to mean exactly this.
Bold heading — many notes use a variable name as a bolded heading or caption directly above a table or a definition. If that bolded text exactly matches a real variable name, it's treated as a confident match.
Sweep-pattern — some documents write a variable as a template, like HTyyU, alongside a list of the sweep years yy stands for. Recognising this pattern and substituting each year in turn is how a single mention like this can correctly resolve to eleven or more real variables, instead of only the one example the author happened to spell out in full.
Plain-text scan — the fallback for long narrative documents with no structured field, no bold headings, and no repeated pattern: any word in the body text that happens to exactly match a real variable name. This is the only method used on most narrative data notes, since they're written as continuous prose.

Confidence levels, and why nothing is automatic

The four methods above don't carry equal trust, and the difference matters more than it might sound. The dictionary holds over 28,000 variable names — with that many, a good number of them are short, ordinary-looking words. sex, own, hand, and inch are all genuine variable names. A plain-text scan of any document, on any topic, will turn some of these up purely by coincidence, with nothing to do with what the document is actually about.

So every match carries a confidence level based on which method found it, and each level is treated differently on a document page:

  • High confidence — topsheet field, bold heading, or sweep-pattern matches. Shown up front, with a checkbox on every row — ticked if it's already in your basket — plus an Add all to basket button that ticks and adds every one in a single click.
  • Medium confidence — plain-text scan matches on longer words (five characters or more), where a coincidental match is less likely. Shown collapsed, with a per-row checkbox but no bulk action — worth a look, but not added all at once.
  • Low confidence — plain-text scan matches on short words (four characters or fewer), exactly the length where a real variable name is most likely to collide with an ordinary word. Shown collapsed, separately, with a short explanation of why they need a second look. There's no bulk action here either — only the per-row checkbox, so nothing is added without someone specifically ticking that one variable.
Medium- and low-confidence matches are never added to a basket automatically, and never appear in an "Add all" action, however tempting it might be to widen that button to save clicks. A plain-text match being wrong isn't rare enough to risk — it's the expected outcome on any sufficiently long document.

When a variable has been renamed

Some documents describe a variable that no longer exists under the name written in the document. A note investigating a bug in a variable called SC53 might conclude with a fix that gets published under a different name entirely — sc53u, say — once the correction goes live. The note is still the correct, useful explanation of how sc53u came to be, but no amount of scanning its text against today's dictionary will ever find that connection, because SC53 simply isn't in the dictionary anymore.

Two things happen for a case like this:

  • A suggestion, automatically. Any bold text shaped like a variable name but missing from the dictionary is compared against every real variable name for a close spelling match. For SC53, this correctly proposes sc53u as the closest match, together with its label, so a reviewer can confirm it at a glance rather than searching by hand.
  • A confirmation, by a person. Once someone's checked a suggestion and agrees it's right, that gets recorded explicitly against the document — not inferred again every time the page rebuilds. From then on, the link between the old name in the note and the real current variable is as solid as any other match on the page.

The suggestion step exists to make the confirmation step fast, not to replace it. A spelling-similarity match is still a guess, and guesses about which variable a historical bug-fix note refers to are exactly the kind of thing that should have a person's name behind them before it's presented as fact.

Adding variables from a document

Every document page has a variables panel reflecting everything described above, split into up to three boxes by confidence. High-confidence variables are listed with their labels in a green box, open by default, each with a checkbox that's already ticked if the variable is in your basket, plus a single Add all to basket button for taking the whole set in one click — this writes straight to your basket the same way every other "Add to basket" checkbox on OWL does, so it shows up immediately wherever else you're working. Medium-confidence matches sit in a collapsed blue box, and low-confidence matches in a collapsed amber box beneath that — each with its own per-row checkbox but no bulk option, so picking up a genuinely relevant plain-text match is still one click away; it's only the all-at-once action that's withheld there.

Where a document has a confirmed relationship to a variable under a different name — the renamed-variable case above — that variable is shown alongside the document's other high-confidence matches once confirmed, with a note explaining that it's linked via a historical name rather than a direct mention in the text.

Create documentation online

If you'd rather not start from a blank Word document, Create Documentation Online lets you build your topsheet and documentation directly in the browser instead — add sections, subheadings, lists, tables, and images through a simple form, with a live preview showing how it'll actually look as you go. Every field a real topsheet has is collected, not just the five that end up public, since the rest is still needed for internal record-keeping.

When you're happy with it, download it as a real Word document to send to us — and if you'd rather finish it offline instead, you're completely free to keep editing that downloaded file directly in Word, the same as any other documentation.

Check your formatting before you submit

Everything above describes how a document gets read once it reaches this section — how it's classified, how variables get linked, what earns high confidence versus a second look. Page Proof is a small offline tool that lets you check your own documentation against those same rules before you send it, rather than finding out afterwards.

Double-click the program to open it, then follow the instructions included with it to check your document. It produces two things: a short report flagging anything worth double-checking — an accidental numbered heading, a blank field in the topsheet table, a stray character in a variable name — and a preview showing roughly how the document will look once it's live, styled to match this site. Nothing is uploaded anywhere and no internet connection is needed; everything happens on your own machine, and the two files it creates are only for your own review before you send the real document on as normal.

Page Proof checks formatting — it doesn't tell you what to write or validate variable names against the dictionary, since a topsheet very often documents variables that don't exist anywhere yet. For guidance on how to structure and write documentation itself, see the rest of this page.
